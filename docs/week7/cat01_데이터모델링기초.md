## 1. 모델링이란?

- 현실 세계를 단순화·추상화하여 일정한 표기법으로 표현하는 것
- **모델링의 3가지 특징**: 추상화, 단순화, 명확화
- **모델링의 3가지 관점**:
  1. 데이터 관점: 업무가 어떤 데이터와 관련이 있는지
  2. 프로세스 관점: 업무가 실제로 어떻게 처리되는지
  3. 데이터와 프로세스의 상관 관점: 데이터와 프로세스가 어떤 관계인지

---

## 2. 데이터 모델링의 3단계

| 단계 | 설명 |
|------|------|
| 개념적 데이터 모델링 | 추상화 수준 높음, 업무 중심, ERD 작성 |
| 논리적 데이터 모델링 | 정규화, 속성/관계 상세화, 재사용 가능 |
| 물리적 데이터 모델링 | 실제 DB 저장 구조로 변환, 성능 고려 |

---

## 3. 데이터 독립성

데이터베이스의 3단계 구조(외부/개념/내부 스키마)로 인해 하위 스키마가 변경되어도 상위 스키마에 영향을 주지 않는 것

| 스키마 | 설명 |
|--------|------|
| 외부 스키마 (External) | 사용자 관점, 개별 뷰 |
| 개념 스키마 (Conceptual) | 전체 DB 논리 구조, 통합 관점 |
| 내부 스키마 (Internal) | 물리적 저장 구조 |

- **논리적 데이터 독립성**: 개념 스키마 변경이 외부 스키마에 영향 X
- **물리적 데이터 독립성**: 내부 스키마 변경이 개념 스키마에 영향 X
- **사상(Mapping)**: 외부-개념 간, 개념-내부 간 연결

---

## 4. 데이터 모델의 3가지 구성요소

1. **엔터티(Entity)**: 업무에서 관리해야 할 데이터의 집합
2. **속성(Attribute)**: 엔터티가 가지는 성질이나 특성
3. **관계(Relationship)**: 엔터티 간의 연관성

> 현실 세계의 모든 데이터는 이 3가지 구성요소로 표현 가능하다.

---

## 5. 좋은 데이터 모델의 요소

| 요소 | 설명 |
|------|------|
| 완전성 | 업무에서 필요로 하는 모든 데이터가 모델에 정의되어야 함 |
| 중복배제 | 하나의 DB 내에 동일한 사실은 1번만 기록되어야 함 (ex. 고객·주문 테이블에 '주소' 중복 ← FK로 해결) |
| 업무규칙 | 업무 규칙이 데이터 모델에 표현되어야 하고, 모든 사용자가 공유할 수 있도록 제공되어야 함 |
| 데이터 재사용 | 데이터의 통합성과 독립성에 대해 고려해야 함. 회사 전체 관점에서 공통 데이터를 도출하고 전 영역에서 사용할 수 있도록 설계 (파일시스템처럼 부서별로 데이터를 따로 만들지 말라는 것) |
| 의사소통 | 업무규칙은 엔터티, 서브타입, 속성, 관계 등의 형태로 최대한 자세히 표현해야 하며, 관련자들이 동일한 의미로 받아들여 활용할 수 있어야 함 |
| 통합성 | 동일한 데이터는 조직의 전체에서 1번만 정의되고, 이를 다른 영역에서 참조·활용해야 함 |

## 6. ERD(Entity Relationship Diagram)

- 테이블 간 서로의 상관 관계를 그림으로 도식화한 것
- 관계의 의미를 직관적으로 표현할 수 있는 수단
- **구성요소**: 엔터티(Entity), 관계(Relationship), 속성(Attribute)

### ERD 작성 순서
1. 엔터티를 그린다.
2. 엔터티를 적절하게 배치한다. (선이 꼬이지 않게, 가장 중요한 엔터티는 왼쪽 상단에 배치)
3. 엔터티 간 관계를 설정한다. (식별자 관계를 우선 설정, Cycle 관계 발생하지 않도록)
4. 관계명을 기술한다. (현재형 사용, 지나치게 포괄적인 단어 지양)
5. 관계의 참여도를 기술한다. (관계차수: 1:N, 1:1, M:N)
6. 관계의 필수/선택 여부를 기술한다. (필수여부는 원을 이용하여 표시(IE))

### ERD 표기법
- **IE(Information Engineering) / Crow's Foot 표기법**: 실무에서 많이 사용
- **Chen 표기법**: 직사각형(엔터티), 마름모(관계), 타원(속성)

---

## 7. 엔터티(Entity)

### 엔터티 개념
- 업무에서 관리해야 할 데이터의 집합
- 실체, 사건, 개념 등의 명사

### 엔터티 유형

**유무형에 따른 분류:**
| 유형 | 설명 | 예 |
|------|------|----|
| 유형 엔터티 | 물리적 형태 있음 | 사원, 물품 |
| 개념 엔터티 | 물리적 형태 없음 | 조직, 보험상품 |
| 사건 엔터티 | 업무 수행 시 발생 | 주문, 청구 |

**발생시점에 따른 분류:**
| 유형 | 설명 |
|------|------|
| 기본(키) 엔터티 | 독립적으로 생성, 타 엔터티의 부모 역할 |
| 중심(메인) 엔터티 | 기본 엔터티로부터 발생, 업무의 중심 |
| 행위 엔터티 | 두 개 이상의 부모 엔터티로부터 발생 |

### 엔터티 특징
- 업무에서 필요로 하고 관리하고자 하는 정보
- 유일한 식별자가 있어야 함
- 2개 이상의 인스턴스 집합이어야 함
- 반드시 속성이 있어야 함
- 다른 엔터티와 최소 1개 이상의 관계가 있어야 함

### 엔터티 명명규칙
- 현업에서 사용하는 용어 사용
- 약어 사용 지양
- 단수 명사 사용
- 유일한 이름 부여

---

## 8. 속성(Attribute)

### 속성 정의
- 엔터티에서 관리되는 구체적인 정보 항목
- 의미상 더 이상 분리되지 않는 최소 데이터 단위

### 속성 분류

**특성에 따른 분류:**
| 유형 | 설명 |
|------|------|
| 기본 속성 | 업무 분석으로 도출된 속성 |
| 설계 속성 | 데이터 모델링 과정에서 설계자가 필요에 의해 도출 |
| 파생 속성 | 다른 속성의 값으로부터 계산·변형되어 생성 (가급적 사용 X) |

**엔터티 구성방식에 따른 분류:**
| 유형 | 설명 |
|------|------|
| PK 속성 | 엔터티 식별자 역할 |
| FK 속성 | 다른 엔터티와 관계를 맺는 속성 |
| 일반 속성 | PK/FK가 아닌 일반 속성 |

**속성 값의 분류:**
| 유형 | 설명 |
|------|------|
| 단일값 속성 | 속성에 하나의 값만 가짐 |
| 다중값 속성 | 여러 값을 가질 수 있음 → 별도 엔터티로 분리 필요 |
| 단순 속성 | 더 이상 분리 불가 |
| 복합 속성 | 여러 세부 속성으로 구성 (ex. 주소 = 시군구 + 상세주소) |

### 도메인(Domain)
- 각 속성이 가질 수 있는 값의 범위

---

## 9. 관계(Relationship)

### 관계 정의
- 엔터티의 인스턴스 사이의 논리적인 연관성

### 관계 페어링
- 엔터티 안의 인스턴스들이 개별적으로 관계를 맺는 것

### 관계 분류
| 유형 | 설명 |
|------|------|
| 존재 관계 | 엔터티 간 상태로 관계 성립 (ex. 사원 - 부서) |
| 행위 관계 | 특정 행위로 인해 관계 성립 (ex. 고객 - 주문) |

### 관계 표기법 요소
- **관계명(Membership)**: 관계의 이름 (명명 규칙: 애매한 동사 피하기, 현재형으로 표현)
- **관계 차수(Degree)**: 각 관계에 참여할 수 있는 인스턴스의 수 → 1:N, 1:1, M:N
- **관계선택사양(선택성)**: 필수참여관계(표기: |), 선택참여관계(표기: ○)

### 관계 체크사항
1. 2개의 엔터티 사이에 관심있는 연관 규칙이 존재하는가?
2. 2개의 엔터티 사이에 정보의 조합이 발생하는가?
3. 업무기술서, 장표에 관계연결에 대한 규칙이 서술되어 있는가?
4. 업무기술서, 장표에 관계연결을 가능하게 하는 동사가 있는가?

## 10. 키(Key)의 종류

| 키 종류 | 설명 |
|---------|------|
| 수퍼키 (Super Key) | 유일성을 만족하는 속성 또는 속성의 집합 (최소성은 불필요) |
| 후보키 (Candidate Key) | 유일성 + 최소성을 모두 만족하는 속성 또는 속성의 집합 (PK가 될 수 있는 키) |
| 기본키 (Primary Key) | 후보키 중에서 선택된 하나의 키 (NOT NULL, UNIQUE) |
| 대체키 (Alternate Key) | 후보키 중 기본키로 선택되지 않은 나머지 키 |
| 외래키 (Foreign Key) | 다른 테이블의 PK를 참조하는 속성 |

- **유일성**: 키로 하나의 행을 고유하게 식별할 수 있음
- **최소성**: 꼭 필요한 속성만으로 구성 (불필요한 속성 포함 X)

## 11. 식별자(Identifier)

### 식별자 개념
- 엔터티 내에서 각각의 인스턴스를 유일하게 구분할 수 있는 구분자

### 식별자 특징
| 특징 | 설명 |
|------|------|
| 유일성 | 주식별자에 의해 모든 인스턴스가 유일하게 구분 |
| 최소성 | 주식별자를 구성하는 속성의 수가 최소한이어야 함 |
| 불변성 | 주식별자가 지정되면 값이 변하지 않아야 함 |
| 존재성 | 주식별자가 지정되면 반드시 값이 있어야 함 (NOT NULL) |

### 식별자 분류

| 분류 기준 | 종류 |
|-----------|------|
| 대표성 | 주식별자 / 보조식별자 |
| 생성여부 | 내부식별자 / 외부식별자(FK) |
| 속성 수 | 단일식별자 / 복합식별자 |
| 대체여부 | 본질식별자 / 인조식별자 |

- **주식별자**: 엔터티를 대표하는 식별자 (NOT NULL, UNIQUE)
- **보조식별자**: 인스턴스를 구분하지만 대표하지 않음
- **내부식별자**: 엔터티 내부에서 스스로 만들어짐
- **외부식별자**: 다른 엔터티와의 관계(FK)로 만들어짐
- **본질식별자**: 업무에 의해 만들어지는 식별자
- **인조식별자**: 업무적으로 없어서 인위적으로 만든 식별자 (ex. 일련번호)

### 식별자 도출 기준
1. 해당 업무에서 자주 이용되는 속성 우선
2. 명칭, 내역 등과 같이 이름으로 기술되는 속성은 주식별자로 지정 지양
3. 복합 식별자의 경우 너무 많은 속성이 포함되지 않도록 함

### 식별자 관계 vs 비식별자 관계

| 구분 | 식별자 관계 | 비식별자 관계 |
|------|-------------|---------------|
| 표기 | 실선 | 점선 |
| 자식 PK 포함 | 부모 PK가 자식 PK의 일부 | 부모 PK가 자식 일반 속성 |
| NULL 허용 | NOT NULL | NULL 허용 |
| 특징 | 강한 연결 | 독립적 존재 가능 |
